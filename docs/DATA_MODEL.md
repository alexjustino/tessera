# Data model

The authoritative schema is `src-tauri/migrations/`. This document explains _why_ it is shaped
the way it is; the SQL explains what it is.

## The two nouns

> An **item** is a unit of work. It lives in a **collection**, which declares **properties**,
> and it carries a document of **blocks**.
>
> An **event** is a unit of time. It lives in a **calendar**, and it has a start, an end, a
> timezone and recurring occurrences with per-occurrence exceptions.
>
> A **time block** joins them: the task reserved on the calendar.

Collapsing the two into one table is tempting and wrong (ADR-008). An event's start/end,
timezone and exception handling do not fit an entity-attribute-value property bag without making
the calendar slow and the task model muddy. What they _do_ share is the important half — the
same block editor, the same reminder pipeline, the same search index, the same activity trail —
and sharing those is what makes `time_block` a two-column table instead of a synchronisation
problem.

This single structure is why one engine serves what Microsoft To Do calls a list, what Trello
calls a board and what Notion calls a database.

## Tables

| Table                 | Holds                                                   |
| --------------------- | ------------------------------------------------------- |
| `workspace`           | one row: name, settings, `schema_version`               |
| `collection`          | a list / board / database                               |
| `property`            | a typed field declared on a collection                  |
| `item`                | a unit of work, optionally nested under another         |
| `item_property_value` | the entity-attribute-value store for property values    |
| `tag`, `item_tag`     | global labels                                           |
| `block`               | the document, for an item, an event or a page           |
| `view`                | a saved query: filters, sorts, grouping, visible fields |
| `reminder`            | a pending alert for an item or an event                 |
| `activity`            | the history and undo trail                              |
| `search_fts`          | FTS5 over titles and flattened block text               |

Arriving with the calendar slice: `calendar`, `event`, `event_exception`, `time_block`,
`work_hours`. Arriving later: `item_dependency`, `time_entry`, `page`.

## Conventions

**Identifiers** are opaque text, generated by the application. **Timestamps** are UTC ISO-8601
strings (ADR-013) — local wall-clock time is never stored, and all-day events are the single
declared exception. **Positions** are fractional index strings (ADR-006), so dragging a card is
one UPDATE of one row rather than a rewrite of the list. **JSON columns** (`config_json`,
`content_json`, `value_json`) hold shapes the domain layer validates; SQLite is not asked to
understand them.

## Three decisions worth defending

**Entity-attribute-value for property values.** EAV is famously slow to query in SQL. It does
not bite here because filtering runs in memory (ADR-004), and in exchange the user creates and
deletes typed properties without dynamic DDL — which is the only alternative, and is far worse
to migrate and back up. The exit, if a profile ever demands it: materialise the three to five
most-queried properties into columns.

**Recurrence stored as a rule, never as rows.** `recurrence_rrule` plus
`recurrence_mode ∈ {schedule, after_completion}`. Occurrences are computed on demand. Writing
them out would turn one weekly task into thousands of rows and make "edit this and all
following" impossible to express. `after_completion` — "three days after I finish it" — is
what maintenance work actually needs and is what Microsoft To Do cannot say.

**A standalone FTS5 table.** `search_fts` is written by the repository, which flattens a block
document to plain text, rather than being an external-content table bound to a source. Binding
it would mean a web of triggers across four owner tables; writing it explicitly costs one call
at the point of change and keeps the schema legible.

## One retraction worth knowing about

Migration 001 gave `item` a `status_id` column, on the assumption that status
would be special. It is not: status is a property like any other, which is
precisely what lets the board group by _any_ select property rather than by one
privileged column.

The column was never written to, so migration 003 drops it. Removing a column we
guessed at is cheaper today than explaining it in a year — and because
migrations are forward-only, the retraction is itself a migration, applied to
every existing database exactly once.

## Migrations

Numbered, forward-only, each applied inside a transaction, each bumping `workspace.schema_version`.

There is no down-migration. A mistake is corrected by a new migration, never by rewriting an
applied one: an applied migration is history, and that history already ran on somebody's
machine.

Every release that adds a migration must be covered by a round-trip test that opens a database
at version N-1 and migrates it without loss. `src-tauri/src/db/migrations.rs` holds those tests.
